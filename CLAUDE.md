# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Stack

Next.js 16 (App Router, `src/` dir, Cache Components) · React 19 · TypeScript (strict) · Tailwind CSS v4 · Better Auth · Drizzle ORM · Neon Postgres. The storefront has a home page and product pages; the product catalog lives in Postgres.

## Commands

Use **pnpm only**: never `npm`, `npx` or `yarn`. Run one-off CLIs with `pnpm dlx`, add packages with `pnpm add` (`-D` for dev). The lockfile is `pnpm-lock.yaml`; never create a `package-lock.json`.

```bash
pnpm install         # install dependencies
pnpm dev             # Next.js dev server (Turbopack)
pnpm build           # production build
pnpm lint            # ESLint (flat config, next core-web-vitals + typescript)
pnpm typecheck       # `next typegen` then `tsc --noEmit`
pnpm db:generate     # SQL migrations into drizzle/ from src/db/schema.ts
pnpm db:migrate      # apply migrations to Neon
pnpm db:push         # push schema directly (prototyping only)
pnpm db:studio       # Drizzle Studio
pnpm db:seed         # wipe and reload the catalog from src/db/seed-data.ts (dev only)
pnpm auth:generate   # generate Better Auth tables into src/db/auth-schema.ts
pnpm db:make-admin <email>  # promote an existing user to the admin role
```

No test framework is set up yet, so there is no test command.

## Environment

Copy `.env.example` to `.env.local`. `DATABASE_URL` (Neon pooled connection string) is required for `dev` and `build`: `src/db/index.ts` throws at import time if it is missing. Better Auth also needs `BETTER_AUTH_SECRET` and `BETTER_AUTH_URL` (the latter is also the origin used for Stripe return URLs). Checkout needs `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET` (`stripe listen --forward-to localhost:3000/api/stripe/webhook` locally) and `CRON_SECRET`; `src/lib/stripe.ts` only throws when Stripe is actually used, so `dev` and `build` work without them. `drizzle.config.ts` loads env files with `@next/env`, so Drizzle Kit reads the same `.env.local` as Next.

## Architecture

- **Database**: `src/db/index.ts` exports a single `db` built with the Neon HTTP driver (`drizzle-orm/neon-http`), typed with everything exported from `src/db/schema.ts`. `schema.ts` is the single entry point for tables: Drizzle Kit, the `db` client, and the Better Auth adapter all read it, so new table files must be re-exported from there.
- **Auth**: `src/lib/auth.ts` is the Better Auth server instance using the Drizzle adapter (`provider: "pg"`, same schema). Email + password only (no verification, reset or social login yet), 30-day persistent sessions with no `cookieCache` (so role changes and revocation apply on the next request), and the `admin()` plugin for `user.role` (`"user"` by default). The `nextCookies()` plugin must stay **last** in `plugins` so Server Actions can set cookies. All auth HTTP traffic goes through the catch-all `src/app/api/auth/[...all]/route.ts`. `src/lib/auth-client.ts` is the React client (same-origin by default).
- **Server-only boundary**: `src/db/index.ts` and `src/lib/auth.ts` import `server-only`; never import them from Client Components. Use `authClient` on the client.
- **Next config**: `cacheComponents` and `partialPrefetching` are enabled in `next.config.ts`, so data fetching follows the Cache Components model (`"use cache"`, Suspense boundaries for dynamic data). Tailwind v4 runs through the `@tailwindcss/turbopack` loader.
- **Design system**: everything lives in `src/app/globals.css`. Raw tokens (`--ink`, `--canvas`, `--gutter`, ...) are on `:root`; static theme values sit in `@theme static`; tokens pointing at runtime vars sit in `@theme inline` so the `theme-inverse` scope can flip them. Tailwind's default color palette, radii and shadows are reset: use the semantic tokens and the `btn`, `link`, `input`, `container-*`, `grid-products`, `media-*` and `type-*` primitives.
- **Typed routes**: layouts/pages use the global `LayoutProps<"/">` / `PageProps` helpers generated by `next typegen` (that is why `typecheck` runs typegen first).
- Path alias: `@/*` → `src/*`.

## Database conventions

- **Tables**: catalog tables live in `src/db/catalog-schema.ts` (`categories`, `products`, `product_stock`). Put new domains in their own `*-schema.ts` file, re-exported from `schema.ts`.
- **Columns**: give every column an explicit snake_case name (`integer("category_id")`); there is no `casing` config. Primary keys are `integer` identity columns. Timestamps are `timestamptz` (`created_at`, `updated_at`).
- **Money**: integer cents (`price_cents`), never floats or numeric. Convert to dollars only in the row mapper.
- **Stock**: one `product_stock` row per product and size (`"One size"` for single-size items), with `position` for display order. It is stock only, not a variant system: no per-size SKU, price or image.
- **Lists read with their parent** (images, details, colors) are typed `jsonb` (`.$type<T[]>()`), not child tables.
- **Foreign keys**: `restrict` for lookups (product → category), `cascade` for owned rows (stock → product). Enforce invariants with `check` constraints (price > 0, quantity >= 0).
- **Imports in schema files are relative** (`../lib/images`): Drizzle Kit does not resolve the `@/` alias.
- **Reads**: pages never query `db` directly. They call server-only getters (`src/lib/product-queries.ts`) that use `"use cache"` + `cacheTag("products")` and map rows to the domain types in `src/lib/products.ts`. That types file must not import the database, because Client Components import it. After any write that changes products or stock, call `revalidateTag("products", { expire: 0 })` (Next 16 needs the second argument) from a Server Action or Route Handler, never during render.
- **Migrations**: change the schema, run `pnpm db:generate`, review the SQL in `drizzle/`, then `pnpm db:migrate`. Never edit a migration that has been applied. `db:push` is for throwaway prototyping only.
- **Scripts outside Next** (seed, one-off tools) build their own Neon client: `src/db/index.ts` imports `server-only`, which throws outside Next. They run with `tsx` and load env with `@next/env`.
- **Scope**: the schema covers products, categories, stock, orders (`src/db/orders-schema.ts`: `orders`, `order_items`, `stripe_events`) and the Better Auth tables. The cart is a cookie, not a table. Do not add carts, refunds tables, reviews, wishlists or variants unless asked.
- **No interactive transactions**: the Neon HTTP driver throws on `db.transaction()`. Get atomicity from `db.batch([...])`, single-statement CTEs and `check` constraints (the `product_stock` quantity check is the oversell guard).
- **Seed**: `pnpm db:seed` truncates with `cascade`, which also wipes `order_items`. Dev only.

## Auth conventions

- **Session access**: `src/lib/session.ts` is the only place that reads the session (`getSession`, `requireUser(returnTo)`, `requireAdmin(returnTo)`, `isAdmin`). It reads `headers()`, so callers sit behind `<Suspense>` (build error otherwise) and never inside `"use cache"`. Pass only a resolved `user.id` into cached functions.
- **Authorization is per page, Server Action and Route Handler.** `src/proxy.ts` only checks that a session cookie exists for `/account/*` and `/admin/*` (a fast redirect, not security), and layouts do not re-run on every navigation. Every new page under those paths, and every Server Action that touches customer or admin data, must call `requireUser`/`requireAdmin` itself.
- **Admin pages** use `export const instant = false` and call `requireAdmin` before rendering (no Suspense shell), so a signed-in non-admin gets a real 404 status. Do not use `forbidden()`: it needs the experimental `authInterrupts` flag.
- **Redirects after sign-in** go through `safeRedirectPath` (`src/lib/safe-redirect.ts`); never `router.push` a raw `next` param.
- **First admin**: sign up in the store, then `pnpm db:make-admin <email>`. There is no admin-promotion UI.

## Checkout and orders conventions

- **Trust boundary**: the cart cookie only says which product, size, color and quantity. Names, prices, stock, shipping (`src/lib/checkout-config.ts`) and currency always come from Postgres or code, and are re-read at checkout start (`startCheckout` in `src/app/checkout/actions.ts`). Line items use inline `price_data` built from DB rows; there is no Stripe product catalog.
- **Stock is reserved when checkout starts**: `reserveOrder` (`src/lib/orders.ts`) inserts a `pending` order and decrements `product_stock` in one `db.batch`. `releaseOrder` gives it back exactly once (CTE guarded by `payment_status = 'pending' AND stock_released_at IS NULL`). Each customer may have one pending order (partial unique index). Holds last `CHECKOUT_HOLD_MINUTES` and match the Stripe session `expires_at`.
- **Only Stripe says an order is paid**: never from the success page, a URL param or a cookie. Every path (webhook, success page's `confirmCheckout`, cron) retrieves the Session from Stripe and calls `settleSession` (`src/lib/checkout.ts`), which is idempotent. `markPaid` verifies session id, currency, subtotal, shipping and total against the order; a mismatch is never marked paid.
- **Webhook** (`src/app/api/stripe/webhook/route.ts`): raw body plus signature check, `stripe_events` log for dedup, guarded transitions as the real protection, 500 on failure so Stripe retries. Handled events: `checkout.session.completed`, `.async_payment_succeeded`, `.async_payment_failed`, `.expired`.
- **Reconcile**: `src/app/api/cron/reconcile-orders` (Bearer `CRON_SECRET`, closed when unset) settles stale pending orders from Stripe. It needs a scheduler from the host.
- **Layering**: `orders.ts` is DB only (no Stripe, no `revalidateTag`); `checkout.ts` joins DB and Stripe and revalidates. Server Actions call `requireUser` and scope order reads by `user_id`.
- **Payment methods** are managed in the Stripe Dashboard (this API version has no `payment_method_types`). Delayed methods are safe because the async events are handled.

## Changing the auth schema

`src/db/auth-schema.ts` was generated and then edited by hand (`timestamptz` columns, `role` default `'user'`, text ids owned by Better Auth). If you add or change a Better Auth plugin, regenerate to a scratch path, diff against it, and apply only the new columns/tables; never overwrite the file blindly.

1. The `auth` CLI cannot load a config that imports `server-only`. Temporarily remove `import "server-only"` from `src/lib/auth.ts` **and** `src/db/index.ts`, run with a placeholder env and `--yes`: `DATABASE_URL=postgresql://u:p@localhost/db BETTER_AUTH_SECRET=placeholder-placeholder-placeholder-00 pnpm dlx auth@1.7.10 generate --config src/lib/auth.ts --output <path> --yes` (`pnpm auth:generate` prompts interactively). Restore both imports afterwards. `@better-auth/cli` is deprecated and stopped at 1.4.x.
2. Keep `export * from "./auth-schema";` in `src/db/schema.ts`.
3. `pnpm db:generate`, review the SQL, then `pnpm db:migrate`.

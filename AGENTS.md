# Atelier Store

This file provides guidance to AI coding agents working with code in this repository.

Next.js 16 (App Router, `src/`, Cache Components) storefront with accounts, cart, Stripe hosted Checkout and an admin area, on Better Auth, Drizzle and Neon Postgres. The product catalog lives in Postgres.

## Commands

Use **pnpm only**: never `npm`, `npx` or `yarn`. Run one-off CLIs with `pnpm dlx`, add packages with `pnpm add` (`-D` for dev). The lockfile is `pnpm-lock.yaml`; never create a `package-lock.json`. Scripts are in `package.json`.

- Run `pnpm typecheck` (typegen first, then `tsc`), `pnpm lint` and `pnpm check:admin` after changes. There is no test framework yet.
- `pnpm db:seed` wipes and reloads the catalog (dev only). `pnpm db:push` is for throwaway prototyping only.

## Environment

`DATABASE_URL` (Neon pooled connection string) is required for `dev` and `build`: `src/db/index.ts` throws at import time without it. Checkout also needs `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET` and `CRON_SECRET`; `src/lib/stripe.ts` only throws when Stripe is actually used, so `dev` and `build` work without them. `BETTER_AUTH_URL` is also the origin used for Stripe return URLs. Locally the webhook needs `stripe listen --events checkout.session.completed,checkout.session.async_payment_succeeded,checkout.session.async_payment_failed,checkout.session.expired --forward-to localhost:3000/api/stripe/webhook` (the CLI requires `--events`). Drizzle Kit and the scripts load env with `@next/env`, so they read the same `.env.local` as Next.

## Architecture

- **Database**: `src/db/schema.ts` is the single entry point for tables (Drizzle Kit, the `db` client in `src/db/index.ts` and the Better Auth adapter all read it), so new table files must be re-exported from there.
- **Auth**: `src/lib/auth.ts` is the Better Auth server instance. Email + password only (no verification, reset or social login yet), no `cookieCache` (so role changes and revocation apply on the next request), and the `admin()` plugin for `user.role`. The `nextCookies()` plugin must stay **last** in `plugins` so Server Actions can set cookies.
- **Server-only boundary**: `src/db/index.ts` and `src/lib/auth.ts` import `server-only`; never import them from Client Components. Use `authClient` on the client.
- **Cache Components**: data fetching uses `"use cache"` and Suspense boundaries for dynamic data. Typed routes use the global `LayoutProps` / `PageProps` helpers generated by `next typegen`.
- **Design system**: everything lives in `src/app/globals.css`. Tailwind's default color palette, radii and shadows are reset: use the semantic tokens and the `btn`, `link`, `input`, `container-*`, `grid-products`, `media-*` and `type-*` primitives. Tokens that point at runtime vars sit in `@theme inline` so the `theme-inverse` scope can flip them.

## Database conventions

- **Schema style**: new domains get their own `*-schema.ts`. Every column has an explicit snake_case name (no `casing` config), integer identity primary keys, `timestamptz` timestamps, `jsonb` (`.$type<T[]>()`) for lists read with their parent, `restrict` FKs for lookups and `cascade` for owned rows, `check` constraints for invariants. Imports in schema files are relative: Drizzle Kit does not resolve `@/`.
- **Money**: integer cents (`price_cents`), never floats or numeric. Convert to dollars only in the row mapper.
- **Stock**: one `product_stock` row per product and size (`"One size"` for single-size items). It is stock only, not a variant system: no per-size SKU, price or image.
- **Reads**: pages never query `db` directly. They call server-only getters (`src/lib/product-queries.ts`) that use `"use cache"` + `cacheTag("products")` and map rows to the domain types in `src/lib/products.ts`, which must not import the database because Client Components import it. After any write that changes products or stock, call `revalidateProducts()` (`src/lib/catalog-cache.ts`) from a Server Action or Route Handler, never during render.
- **Migrations**: change the schema, run `pnpm db:generate`, review the SQL in `drizzle/`, then `pnpm db:migrate`. Never edit a migration that has been applied.
- **Scripts outside Next** (seed, one-off tools) build their own Neon client, because `src/db/index.ts` imports `server-only`, which throws outside Next. They run with `tsx`.
- **Scope**: the schema covers products, categories, stock, orders (`orders`, `order_items`, `stripe_events`) and the Better Auth tables. The cart is a cookie, not a table. Do not add carts, refunds tables, reviews, wishlists or variants unless asked.
- **No interactive transactions**: the Neon HTTP driver throws on `db.transaction()`. Get atomicity from `db.batch([...])`, single-statement CTEs and `check` constraints (the `product_stock` quantity check is the oversell guard).
- **Seed** truncates with `cascade`, which also wipes `order_items`.

## Auth conventions

- **Session access**: `src/lib/session.ts` is the only place that reads the session (`getSession`, `requireUser(returnTo)`, `requireAdmin(returnTo)`, `isAdmin`). It reads `headers()`, so callers sit behind `<Suspense>` (build error otherwise) and never inside `"use cache"`. Pass only a resolved `user.id` into cached functions.
- **Authorization is per page, Server Action and Route Handler.** `src/proxy.ts` only checks that a session cookie exists for `/account/*` and `/admin/*` (a fast redirect, not security), and layouts do not re-run on every navigation. Every new page under those paths, and every Server Action that touches customer or admin data, must call `requireUser`/`requireAdmin` itself.
- **Admin pages** use `export const instant = false` and call `requireAdmin` before rendering (no Suspense shell), so a signed-in non-admin gets a real 404 status. Do not use `forbidden()`: it needs the experimental `authInterrupts` flag.
- **Redirects after sign-in** go through `safeRedirectPath` (`src/lib/safe-redirect.ts`); never `router.push` a raw `next` param.
- **First admin**: sign up in the store, then `pnpm db:make-admin <email>`. There is no admin-promotion UI.

## Admin conventions

- **Every** page, Route Handler and Server Action under `src/app/admin` awaits `requireAdmin` before doing any other work (reading `params`/`searchParams` is fine). Actions are directly POSTable, so the layout and page checks do not cover them. `pnpm check:admin` fails on omissions, on `loading.tsx`/`<Suspense>` under admin (they turn the non-admin 404 into a 200), and on admin data modules imported from outside the admin area.
- **Admin data access**: `src/lib/admin-queries.ts` (uncached reads, include hidden products) and `src/lib/admin-catalog.ts` (writes). They do no authorization themselves; only admin pages and actions import them.
- **Form input** is parsed once, server-side, by `parseProductForm` (`src/lib/product-input.ts`); the client form only shows the result. Prices are parsed from strings to integer cents. The slug is set at creation and never updated.
- **Hiding products**: `products.archived_at`. The storefront getters (`findProducts`) skip hidden rows; `getCartProducts` returns them with empty stock so carts and checkout treat them as unavailable. Products are never deleted. `FEATURED_SLUG` cannot be hidden.
- **Stock**: product edits add sizes but never change existing `product_stock` rows (checkouts change them concurrently). Quantities are changed only on `/admin/stock`, through `setStockQuantity`: a compare-and-set that writes only if the row still holds the `expected` quantity the admin saw, parsed by `parseStockForm` (`src/lib/stock-input.ts`). `quantity` is what can be sold now, net of units held by open checkouts. Every stock write calls `revalidateProducts()`.

## Checkout and orders conventions

- **Trust boundary**: the cart cookie only says which product, size, color and quantity. Names, prices, stock, shipping (`src/lib/checkout-config.ts`) and currency always come from Postgres or code, and are re-read at checkout start (`startCheckout` in `src/app/checkout/actions.ts`). Line items use inline `price_data` built from DB rows; there is no Stripe product catalog.
- **Stock is reserved when checkout starts**: `reserveOrder` (`src/lib/orders.ts`) inserts a `pending` order and decrements `product_stock` in one `db.batch`. `releaseOrder` gives it back exactly once (CTE guarded by `payment_status = 'pending' AND stock_released_at IS NULL`). Each customer may have one pending order (partial unique index). Holds last `CHECKOUT_HOLD_MINUTES` and match the Stripe session `expires_at`.
- **Only Stripe says an order is paid**: never from the success page, a URL param or a cookie. Every path (webhook, success page's `confirmCheckout`, cron) retrieves the Session from Stripe and calls `settleSession` (`src/lib/checkout.ts`), which is idempotent. `markPaid` verifies session id, currency, subtotal, shipping and total against the order; a mismatch is never marked paid.
- **Webhook** (`src/app/api/stripe/webhook/route.ts`): raw body plus signature check, `stripe_events` log for dedup, guarded transitions as the real protection, 500 on failure so Stripe retries. It handles `checkout.session.completed`, `.async_payment_succeeded`, `.async_payment_failed` and `.expired`.
- **Reconcile**: `src/app/api/cron/reconcile-orders` (Bearer `CRON_SECRET`, closed when unset) settles stale pending orders from Stripe. It needs a scheduler from the host.
- **Layering**: `orders.ts` is DB only (no Stripe, no `revalidateTag`); `checkout.ts` joins DB and Stripe and revalidates. Server Actions call `requireUser` and scope order reads by `user_id`.
- **Payment methods** are managed in the Stripe Dashboard (this API version has no `payment_method_types`). Delayed methods are safe because the async events are handled.

## Changing the auth schema

`src/db/auth-schema.ts` was generated and then edited by hand (`timestamptz` columns, `role` default `'user'`, text ids owned by Better Auth). If you add or change a Better Auth plugin, regenerate to a scratch path, diff against it, and apply only the new columns/tables; never overwrite the file blindly.

1. The `auth` CLI cannot load a config that imports `server-only`. Temporarily remove `import "server-only"` from `src/lib/auth.ts` **and** `src/db/index.ts`, run with a placeholder env and `--yes`: `DATABASE_URL=postgresql://u:p@localhost/db BETTER_AUTH_SECRET=placeholder-placeholder-placeholder-00 pnpm dlx auth@1.7.10 generate --config src/lib/auth.ts --output <path> --yes` (`pnpm auth:generate` prompts interactively). Restore both imports afterwards. `@better-auth/cli` is deprecated and stopped at 1.4.x.
2. Keep `export * from "./auth-schema";` in `src/db/schema.ts`.
3. `pnpm db:generate`, review the SQL, then `pnpm db:migrate`.
